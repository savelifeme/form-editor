# 宪章

## 核心原则

### 中文优先与沟通规范
项目中所有文档、代码注释、用户界面和团队沟通都必须使用中文。英文术语只有在没有标准中文翻译时才能使用，且必须提供中文解释。
- 所有规范文档必须使用中文编写
- 代码注释、提交信息、PR描述必须使用中文
- API文档和用户界面文案使用中文
- 英文技术术语首次出现时需注明中文含义
  **理由**：确保项目对所有中文用户友好，降低理解门槛，促进团队协作效率。

### 规范驱动开发
所有功能开发必须从规范（spec）开始；未通过评审的规范禁止编码，所有文档随实现同步。
**理由**：充分前置思考与可测试规范可降低返工并保持团队一致性。

### 测试优先与持续验证
遵循 TDD：先编写失败的测试，再用最小实现通过并重构。
**理由**：测试先行能约束设计、及时暴露缺陷，避免回归风险。

### 渐进式交付与快速反馈
以可独立验证的小颗粒故事交付，分支短生命周期、频繁合并，优先完成 P1 以验证 MVP。
**理由**：小步快跑减少风险，并提供持续反馈以修正方向。

### 简单优先
在满足需求前提下选择最易理解的实现。
**理由**：简单设计可维护性高、错误少，避免无效抽象。

### 最小化更改（只改必要部分）
任何代码或文档修改必须遵循最小化更改原则：只修改完成当前需求所必需的部分，避免过度重构、
大范围格式化、无关重命名或“顺手优化”。每次更改必须能明确对应到业务需求或技术原因。
**理由**：降低引入回归的概率，保持可审查性与可追溯性，缩短评审与回滚路径。

### 禁止无需求兼容性代码
除非有明确的业务需求或性能要求，否则不编写兼容性代码（例如为非目标平台/旧版本/低概率场景
引入额外分支与适配层）。优先保证核心功能的稳定性与可维护性，避免为支持不必要场景增加复杂度。
**理由**：兼容性分支会放大复杂度与测试面，增加维护成本与故障风险。

### 文档要求
必须文档化所有公共 API 接口、业务逻辑与算法、配置参数说明以及部署手册。内容使用清晰中文，附示例，覆盖错误处理与边界条件，并与代码同步更新。

### 治理
- 权威性：本宪章优先于临时做法。例外书面化跟踪。
- 修订流程：通过 PR 修改本文件，给出动机与迁移影响；需技术负责人和另一名评审共同批准。
- 版本策略：本宪章采用语义化版本（MAJOR：不兼容原则变化；MINOR：新增/扩展原则；PATCH：澄清/措辞）。
- 合规审查：每季度对活跃服务进行一次合规检查；违规项必须在下一迭代列入整改任务。

### 合规检查
每个合并请求都必须检查宪法合规性，包括但不限于：
- 是否符合中文优先原则
- 是否遵循规范驱动开发
- 是否遵循测试优先要求
- 代码是否保持简单性
- 文档是否完整
